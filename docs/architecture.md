# Architecture

## Projects

The solution has five projects with a one-way dependency flow (plus `Tests`):

```
Gui ──► SdlGamepads ───► Application ──► Core
  ├───► SkaarhojPanel ──► Application
  └───────────────────────► Application
```

`Core` holds interfaces and models only. `Application` implements commands, devices, and services. `SdlGamepads` (USB joysticks) and `SkaarhojPanel` (the SKAARHOJ panel's joystick and zoom rocker) are the two controller sources. `SkaarhojPanel` also holds the TCP link to the panel (connect, a dead-man that counts any line from the panel and pings it when quiet, reconnect, message parsing; see [skaarhoj-integration.md](skaarhoj-integration.md#the-panel-link-in-this-app)). `Application`'s `CompositeGamepadsService` joins the sources into the one controller list. `Gui` wires everything together in `Program.cs` using Splat's service locator (`services.RegisterConstant(...)`). `Packaging/` holds the macOS app packaging (the Windows zip needs no files of its own, see [development.md](development.md#windows-package)); it is not part of the dependency graph.

## From stick movement to camera movement

1. **Polling.** `SdlGamepadsService.UpdateLoop` runs on a background task every 15 ms. Each tick it first runs the input queued from other threads (`InputQueue`: Companion selections, SKAARHOJ panel input), then drains SDL events (axis motion, button up/down, device added/removed).
2. **Raw value.** `SdlGamepad.OnAxisEvent` maps the SDL value to `-1..1` and sets `Input.InputValue`. For the panel, `SkaarhojGamepad.OnSpeed` maps `HWC#<id>=Speed:<n>` to `n / 500`, clamped to `-1..1`.
3. **Shaping.** The `Input.InputValue` setter applies inversion, deadzone and saturation (linear mapping between them), then calls `ExecuteCommand()`. An axis mapped to a dynamic command can bend that linear part with its **expo** `e` (0..1, default 0, saved per input in `Gamepads.json`, or `SkaarhojGamepads.json` for the panel): `(1 − e)·x + e·x³` of the linear value `x`, for finer speeds near centre. Inside the deadzone is still exactly 0 (stop), the saturation zone still exactly ±1 (max speed), and expo 0 is the linear mapping unchanged. Outside the deadzone a dynamic command never gets a stop: the direction comes from the sign, so even the smallest shaped value is a move at the camera's minimum speed. Static commands ignore expo, so their ±0.25 trigger point does not move. An expo outside 0..1 (from the file) is used as 0 with a `WARN`.
4. **Command.** The input's mapped `ICommand` runs. Dynamic commands (`IDynamicCommand`: pan, tilt, zoom, focus) take a **speed fraction** (0..1 of the axis's full range) and a direction; static commands (`IStaticCommand`: select camera, preset, power…) take a fixed value. An axis's fraction is the shaped value × its **Max speed** percentage (0–100 %, default 100 %); a button's is its **Speed** percentage. A fraction outside 0..1 is clamped with a `WARN`, never thrown. The pan, tilt, zoom and focus commands then scale it by the active **speed profile**'s percentage for their axis (1–100 %; one global list for every camera, see [ADR 0002](adr/0002-global-speed-profiles.md)), so the camera gets shaped value × Max speed (or Speed) % × speed profile %. They read the active speed profile each time they run: a change applies from the next movement, and a held input is not re-sent. A stop stays a stop, a move stays a move however small the product, and a 100 % speed profile changes nothing. Preset recall speed and the controller view's axis readout (the input's own fraction) do not include the speed profile.
5. **Device.** The command calls the gamepad's `SelectedCamera`, an `ICamera`, which maps the speed fraction onto its camera type's protocol. There are two camera types: VISCA and XC (see [the XC send path](#the-xc-send-path)). The VISCA camera (`ViscaDeviceBase`) builds a VISCA packet (always one command per packet) and sends it via `ViscaIpDevice` over UDP (shared socket in `Core/Utils/UdpSocket.cs`) or TCP. Over UDP, replies reach the camera configured with the IP:port they come from; when two cameras share an IP:port, the first opened keeps the replies and the second logs a warning and still sends its commands. `ViscaIpDevice` maps the speed fraction onto VISCA as `Min + floor(f · (Max − Min) + 1e-6)` (pan 1..24, tilt 1..20, zoom and focus 0..7), so at 100 % every deflection sends the same VISCA speed as before fractions; the axis a command stops sends speed 0, and a fraction that quantizes to the speed already sent sends nothing. Pan and tilt share a packet, so a pan or tilt command also sends the other axis's stored speed byte (4 on a new device), even when that axis is stopped, and `Stop()` sends both stored bytes; the camera ignores the speed of a stopped axis.

**Saved speeds.** "Max speed" and "Speed" are saved as the input's command value. A save built from a live gamepad (`new GamepadSettings(gamepad)`: after any settings change, when a plugged-in USB joystick is activated or deactivated, and when the panel is activated while its link is up and it is awake) writes every input with `SpeedIsPercentage: true` and its speed as a percentage; no other save adds the marker. A value without it is a VISCA step `s` saved before #43 (in `Gamepads.json` or `SkaarhojGamepads.json`) and is migrated on load, in memory only, to `ceil(100 · (s − Min) / (Max − Min))` %, the smallest percentage that still sends step `s` at full deflection. The saves that only flip an entry's activation flag (`SdlJoystickActivation.PersistDeactivated`, `SkaarhojGamepadsService.SaveActivated`) write the stored entry back with nothing else changed, as every save does with the file's other gamepad entries, so a legacy step stays an unmarked step until its gamepad is next saved live. A value is never converted twice: the marker is only ever written together with a percentage, and until then each load converts the same step the same way. Values are classified only by the marker, never by size (0, 1, 7, 20 and 24 are valid in both units). Out-of-range values are clamped with a `WARN`. Static command values (presets, preset recall speed 1..24, camera selection) are never converted.

**Relative inputs** (`InputType.Relative`, for encoders such as the SKAARHOJ panel's knobs) carry signed step counts, not a position: clockwise is positive. The controller calls `IInput.Step(steps)` instead of setting `InputValue`. A relative input takes static commands only, like an axis with a static command: each step in the configured direction (High = clockwise, Low = anticlockwise) runs the command once, and the second command runs once per step the other way. Nothing stays pressed or moving. Dynamic commands are not offered; one mapped from saved settings is refused with a `WARN` and the input is left unmapped. More than 100 steps in one event are capped (with a `WARN`) so a faulty device cannot tie up the input loop.

Commands are **event-driven**: a packet is only sent when the shaped input value changes. The one exception is stops: when pan/tilt, zoom or focus goes to stop, `ViscaIpDevice` repeats that packet 3×, at least 50 ms apart (roughly 100–200 ms in all), built from the camera's current state at send time. The XC camera repeats its stops the same way (see below). Motion is not re-sent periodically. When a controller's selected camera changes while the app is driving the previous one (`ICamera.IsMoving`), `DrivenCameras` force-stops it. When a controller is unplugged or deactivated (for the panel: its link goes down, or it falls asleep), its service calls `DrivenCameras.StopAll()`, which force-stops every camera that controller has had selected. See [live-safety.md](live-safety.md) for why this matters.

### The XC send path

The XC camera (`XcCamera`) drives a Canon camera over Canon's XC protocol: HTTP `GET` requests to the camera's `control.cgi`, sessionless (no `s=` session parameter). It supports pan, tilt, zoom, manual focus and preset recall. Focus mode, focus lock, power, preset set and preset reset send nothing and log at `INFO`, at most once per operation per minute; Companion's own Canon module covers them.

- **Wanted state.** `Pan`, `Tilt`, `Zoom`, `Focus`, `Preset` and `Stop` run on the input loop and only record the wanted direction and speed of each axis, or the wanted preset recall, then return; they never wait on the network. A moving pan or tilt axis's speed fraction `f` maps to `round(10 + f · 9990)` (XC speeds 10..10000); a stopped pan or tilt axis sends `stop` at speed 10. A moving zoom or focus maps `f` as VISCA does, to `Min + floor(f · (Max − Min) + 1e-6)`, onto the CR-N500's zoom speeds 0..15 (`tele` for the command's high direction, `wide` for low) and manual-focus speeds 0..2 (`far`, `near`); a stopped zoom or focus sends `stop` at speed 0. These ranges, like the preset ranges below, are the CR-N500's values from appendix A of Canon's XC protocol spec, fixed in `XcCamera` and checked on site, never read from the camera. A request carries only the axis groups whose wanted state changed since they were last sent or whose stop is still being sent (see **Stops**), in this order, each axis's speed before its direction: pan and tilt together (`c.1.pan.speed.dir`, `c.1.pan`, `c.1.tilt.speed.dir`, `c.1.tilt`; a change to either sends both), zoom (`c.1.zoom.speed.dir`, `c.1.zoom`), focus (`c.1.focus.speed`, `c.1.focus.action`). So a zoom move does not resend pan and tilt, and moving several axes at once adds no requests. No other parameter is sent: the camera's own speed mode is used, never set, but every focus request also sets the camera's manual-focus speed.
- **One in flight.** Each XC camera has one background send loop and one `HttpClient` (one keep-alive connection). At most one request (control or probe) is in flight per camera. When the wanted state changes during a request, only the newest state is sent next; the states in between are dropped. Consecutive requests to a camera are at least `MinRequestGap` (30 ms, Canon's recommended minimum) apart, counted from the previous request's completion. Each request times out after 500 ms; a slow or dead camera never delays another camera or the input loop.
- **Success.** A request succeeds only with HTTP 200 and a `livescope-status: 0` header; XC reports its errors as HTTP 200 with another `livescope-status` (301: another client holds camera control). A run of failures logs one `WARN` with the reason (again if the reason changes; a login failure at most once a minute, see **Login**), and the recovery one `INFO` line.
- **Stops.** A stop (pan/tilt, zoom or focus going to stop, or `Stop()`, which stops all four axes even when the app believes them stopped) goes out in the next request, ahead of any pending move, and is sent 3× at least 50 ms apart, each send built from the wanted state at send time, so a move made within the window goes out instead. It rides in every request until it is done, next to any other group that changed, and is retried until one of its sends succeeds or it is given up. A stop none of whose sends succeeded is given up when a send of it fails once it has been sent 3× and the give-up bound (`DefaultStopGiveUpAfter`, 5 s; tune on site) has passed since it started, or, for a stop a failed recall restored, since the restore (see **Preset recall**). Nothing more of it is sent, one `ERROR` names the camera, the axes given up (`pan/tilt`, `zoom`, `focus`; the stops one send gives up, such as a failing `Stop()`'s, share one line), the bound and the last failure, and the idle probe runs again (see **Reachability**). No stop is given up on a send whose outcome is ignored after an address, port or login change (its next failed send decides), nor while a recall is wanted, which takes its place. 5 s exceeds the probe interval plus two request timeouts plus the 50 ms interval (4.05 s), so the camera already shows not reachable when the app gives up. The cost: the app no longer tries to stop that camera, so it may keep moving, even once the network returns, until that axis is moved and released, stopped again, recalled to a preset, or at its limit. A newer move ends a pending pan/tilt stop only when it moves both pan and tilt; a zoom or focus stop ends when its own axis moves. A preset recall goes out ahead of stops and takes their place (see **Preset recall**). From a stop's first send until it is done, every request to the camera but a recall waits 50 ms after the previous one instead of 30 ms.
- **Preset recall.** Recalling the app's preset number `n` (0-based, shown as `n + 1`) sends the camera preset `p = n + 1` in a request of its own; a number outside the CR-N500's presets 1..100 sends nothing and logs a `WARN`. Once *Preset Recall Speed* `v` (1..24) has been set on the camera, every later recall also carries `p.ptzspeed = round(1 + (v − 1) · 99 / 23)` (the CR-N500's preset speeds 1..100); until then a recall sends `p` alone, and the camera moves at the speeds saved with its preset. Setting the recall speed sends nothing by itself, and it is not saved: after a restart, recalls send `p` alone until it is set again. A recall is the next request the camera starts: only the request in flight (a probe included, until it is answered, fails or times out) and the 30 ms gap after it delay it. It never waits the 50 ms stop interval, no pending stop, `Stop()` or pending move holds it back, and no probe starts while a recall is wanted. When it goes out, it takes the place of every stop still pending on pan/tilt, zoom and focus, sent yet or not: none of them is sent while the recall is in flight, and none rides in its request (the spec defines no order for a preset and a stop in one request). If the recall succeeds, those stops end without another send. The only request that may follow it is a move wanted before it and never sent (an axis wanted moving at a direction or speed other than the last one sent for it), sent once. If it fails (no answer within the timeout, a connection error, any answer but HTTP 200 with `livescope-status: 0`, a login refusal included, or an unexpected error), each of those stops is restored as a new stop under the rules above, its 3 sends and its give-up bound counted from the restore, unless a newer action took its place: a newer stop on that group, a move that would end it (see **Stops**), or a newer recall, which goes first and takes its place in turn. A recall is sent once and never retried, whatever its outcome; a failure is logged like any other failed request. Of several recalls called before one goes out, only the newest is sent, with the recall speed set when it was called. `Stop()` keeps a recall not yet sent. Anything wanted after a recall was sent, such as a stop or `Stop()`, goes out after it by the usual rules, even if it cuts the recall short. The cost: a failed recall is not retried, so the camera stays put until the operator recalls again. A recall answered after the 500 ms timeout counts as failed even if the camera ran it, so the stops it restores may cut it short partway. A stop that a failed recall restores goes out only once that recall has completed, up to about one request timeout later, and later again for each newer recall called before then. After a successful recall the app relies on the recall taking over a camera still moving on a manual move and stopping it at the preset, which needs every preset the show recalls to store pan, tilt and zoom (`p.<n>.content.ptz=enabled`, checked on site): a successful recall of a preset that does not may leave running a manual move whose stop it replaced.
- **Reachability.** `Connected` turns true when a request succeeds, and false when one fails and none has succeeded within the probe interval (3 s). An idle camera gets a probe (sessionless `info.cgi?item=s`, read-only) once no request has completed for 3 s; probes start only while no control request (move, stop or recall) is wanted, so a stop waits for the one request in flight, a probe or a recall included, to return or time out, and then goes out next unless a recall is wanted: the recall goes first and takes the stop's place, and a stop that a failed recall restores has waited for that recall too, and for each newer one (see **Preset recall**). A given-up stop is no longer wanted (see **Stops**): once nothing else is, the probe runs on its usual schedule, so a camera that refuses control (301) but answers the probe turns connected again, and one that does not answer stays not reachable. Changing the address or port sends the next request there, with a prompt probe, and resets `Connected` until a request there succeeds. The camera's failure reason is the reason the `WARN` for its failed requests gives (see **Success**), in the same words, whether or not that `WARN` was logged again. It is set when a request to the current address, port and login fails, cleared when one succeeds or the address or port changes, and left as it was by a request whose outcome is ignored; the XC row shows it on a line below its fields while there is one.
- **Login.** A camera that does not allow guest control answers HTTP 401. With a username set (the password is optional), the request is repeated once, straight away, with an `Authorization` header answering that 401's challenge: Digest with MD5 (RFC 7616, `qop=auth` when offered), preferred when the camera also offers Basic, or Basic. The two HTTP requests are one send-path request: they share its 500 ms timeout and its turn in the one-in-flight order, newer wanted state waits for the next request, and the 30 ms gap counts from the repeat. Once the camera has challenged, later requests, probes included, carry the login up front (Basic as is; Digest with the latest nonce and a counting `nc`), so a stop costs no extra round trip. When the camera challenges again (an expired nonce), the request is answered the same way, with no failure logged when the repeat succeeds; that event costs one LAN round trip inside the same timeout, so a stop still waits at most one request timeout for the request in flight. A 401 with no username set, a 401 to the repeat (a wrong login) and a challenge the app cannot answer (another Digest algorithm, `qop=auth-int`, or none) are failures, not repeated, and logged at `WARN` at most once a minute per camera; a challenge is named by its scheme and algorithm only. A change of address, port or login forgets the challenge, so a login only goes to a camera after it has asked for one. The login changes only when the operator presses **Log in** in the XC row, which applies the typed username and password together, as one change, and saves them, or when `Cameras.json` loads; typing in the login fields changes nothing but the row. The send loop takes the two as one pair, so no request carries one field of a new login with the other of the old. A login change applies from the camera's next request, a probe sent as soon as the gap allows when nothing else is wanted; the outcome of the request in flight is ignored, and `Connected` and the failure reason (see **Reachability**) keep their values until a request with the new login settles them. Neither the login nor an `Authorization` value is logged or put in a URL. `livescope-status: 401` on an HTTP 200 is a command failure, never a challenge. The camera answers challenges itself with the platform's HTTP types, not the HTTP handler's `Credentials`: on .NET 10 those paid a 401 round trip on every Digest request and cannot change after the first request.

## Key abstractions

| Type | Purpose |
|---|---|
| `IGamepad` | A controller: its inputs, available commands, camera list, and `SelectedCamera`. `SdlGamepad` (USB joystick) and `SkaarhojGamepad` (the panel's four axes) implement it. |
| `IInput` | One axis, button or relative input (encoder), with its mapped command and shaping settings. |
| `ICommand` | An action on the selected camera. Created per gamepad by `CommandsService`. |
| `ICamera` | A camera of any camera type: movement by speed fraction, stop, presets, power and focus, whether it is connected, whether the app is driving it (`IsMoving`), and its Companion number (what a Companion request selects it by). Everything outside a camera type's own implementation and settings panel uses only this (see [ADR 0001](adr/0001-protocol-neutral-cameras-with-speed-fractions.md)). |
| `ViscaDeviceBase` | The VISCA camera type: implements `ICamera` with VISCA command builders. `ViscaIPDeviceBase` adds the connection settings, and `ViscaIpDevice` sends over UDP or TCP. Outside them, only the camera list's VISCA settings panel and **Add VISCA camera** button and the `Cameras.json` mapping name these types. |
| `XcCameraBase` | The XC camera type (Canon's HTTP control protocol): implements `ICamera` with its settings (name, Companion number, address, port, username and password). `XcCamera` sends the requests (see [the XC send path](#the-xc-send-path)). Outside them, only the camera list's XC settings panel and **Add XC camera** button and the `Cameras.json` mapping name these types. |
| `ISpeedProfilesService` | The one global, ordered list of speed profiles (finest first) and the active one, for every camera. Steps to the next faster or finer speed profile (stopping at either end), sets the active one, and adds, edits, moves and removes speed profiles; each change is saved to `SpeedProfiles.json` and announced with `ProfilesChanged`. Never throws: an invalid request is logged at `WARN` and changes nothing. |
| `IGamepadsService` | Discovers controllers and activates/deactivates them. `SdlGamepadsService` also owns the input loop. `SkaarhojGamepadsService` turns the panel link into one controller. `CompositeGamepadsService` merges them into the single-select controller list, routes each activation to the source that owns it, and keeps only one controller active at a time. |

## Settings

JSON files in the settings folder, which is `%APPDATA%\PTZJoystickControl\` on Windows (`~/Library/Application Support/PTZJoystickControl/` on macOS, `~/.PTZJoystickControl/` on Linux) unless `--settings-dir` names another (see [development.md](development.md#another-settings-folder)). One place resolves it from the command line, `Application/SettingsFolder.cs`; `Program.cs` builds every settings file's path, and the log file's folder, from what it returns. The files: `Cameras.json` for cameras (each entry names its camera type; an XC camera saves its address and port under the VISCA camera's `IpAddress` and `Port` keys, and its login under `Username` and `Password`, unencrypted, each only when it is not empty; an entry that cannot be loaded, such as a camera type from a newer build, is skipped with a `WARN` and the other cameras still load), `Gamepads.json` for input mappings, the optional, hand-edited `Companion.json` for the port the app listens on for Companion (read at startup only; see [companion-integration.md](companion-integration.md#settings-companionjson)), `SkaarhojPanel.json` for the SKAARHOJ panel's address and port (edited by hand; an empty address means no panel), `SkaarhojGamepads.json` for the panel's input mappings (kept apart from `Gamepads.json`, whose every entry is listed as a USB joystick), and `SpeedProfiles.json` for the speed profiles and which one is active. With no `SpeedProfiles.json` the default speed profiles "Fine", "Medium", "Fast" and "Full" are used with "Full" (the fastest, 100 % on every axis) active, and the file is first written when a speed profile changes; a file that cannot be used falls back to the same defaults with an `ERROR`. A usable file whose active position is missing or not between 1 and the number of speed profiles makes its last speed profile (the fastest, whatever its name) active, with a `WARN`, and is not rewritten until a speed profile changes. Settings are saved on every persistent property change, atomically: each save writes a sibling `.tmp` file, flushes it to disk, then moves it over the target.

## Threading

- SDL polling and command execution run on the `UpdateLoop` background task. It is the input loop: no other thread runs gamepad input.
- The Companion HTTP listener runs its callbacks on thread-pool threads, one request at a time. It validates the request against a snapshot of the camera list and only queues each camera selection on `InputQueue`; `UpdateLoop` runs the queued input at the start of every tick, before polling SDL. A queued input that throws is logged and skipped. A speed profile step from Companion is a settings change, not input: the listener applies it itself, after queuing the request's camera selections, through `ISpeedProfilesService`, and never queues it on the input loop, because each speed profile change saves `SpeedProfiles.json` before it returns and a slow disk must never delay joystick → camera control. A slow save delays only the Companion requests behind it (see [companion-integration.md](companion-integration.md#companion--app-speed-profiles)).
- The SKAARHOJ panel link (`SkaarhojPanelLink`) runs on its own background task and raises its events there. `SkaarhojGamepadsService` only queues them on the same `InputQueue`: axis input, link up/down and sleep/wake all run on the input loop, at most one tick (15 ms) later, in the order the link received them. One `InputQueue` is built in `Program.cs` and shared by every source.
- Each XC camera runs one background send loop (see [the XC send path](#the-xc-send-path)). The input loop only records the wanted state under the camera's lock and wakes the loop. The loop raises `Connected` and failure-reason changes; the XC settings panel re-raises them on the UI thread.
- Avalonia UI updates must happen on the UI thread. `SelectedCamera` changes are raised synchronously on the input loop, so `DrivenCameras` and `SelectCameraCommand` see them at once; `CamerasViewModel` re-raises them on the UI thread for bindings.
- Selecting a camera or activating/deactivating a controller from the main window still runs on the UI thread and is not serialized with the input loop. The app is not operated from its window during live use.
- The speed profiles are one immutable snapshot (`SpeedProfileList`). `SpeedProfilesService` builds each change under its lock, publishes the new snapshot, saves it on the calling thread while still holding the lock, then raises `ProfilesChanged` outside the lock. The movement commands read the snapshot on the input loop without locking, so changing a speed profile from the window (on the UI thread) or from Companion (on the listener thread) never blocks input. `SpeedProfilesViewModel` shows each change on the UI thread, whichever thread made it.
- The controller lists are guarded by one lock, `InputQueue.ControllersLock`, shared by every source and `CompositeGamepadsService`. Each source changes its `Gamepads`/`ActiveGamepads` under it, from the input loop and from activation on the UI thread, and the composite reads every source under it. A single lock means the composite can read one source while another is mid-change without a lock-order deadlock. Holding it while a retiring controller stops its cameras is intended: input waits until the stop is sent.
